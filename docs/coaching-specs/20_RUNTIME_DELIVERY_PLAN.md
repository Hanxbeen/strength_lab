# 실기기 연결 전 API 인수 계획
2026-10-18 갱신. 현재 단계는 내부 구현이며 일반 공개 완료가 아니다. 최신 상태는 ../CURRENT.md, 네 종목 적용 결정은 21_FOUR_LIFT_DELIVERY.md를 따른다.

## 완료 목표
실제 로그인한 사용자가 자신의 조건으로 루틴 선택 → 시작 → 수행 변경 → 종료 → 앱 재실행 → 다음 운동을 실행한다.
검증 수준은 코드 / 실제 DB / 배포 HTTPS / iOS를 각각 기록한다. 코드 테스트를 뒤 단계의 증거로 대체하지 않는다.

## 1. 숙련도별 실제 루틴 공급
- 입문: 동작·장비·첫 부하를 모르는 사용자. 교육 경로와 지원 범위를 반환한다. 교육 자료를 실행 루틴 수에 합산하지 않는다.
- 초급: 네 동작을 독립 수행하며 알려진 시작 중량을 등록하는 사용자용 Petrizzo 주2회/3회 구성은 실제 DB 저장·로컬 실행 확인 완료. 감독하 연구와 직접 중량 선택의 차이, 공개 적용 범위, 배포 실사용 검증은 별도로 관리한다. 과거 OHP 생략안은 기록 호환을 위해 보존한다.
- 중간 경험/숙련: PER/Helms/METD 각각의 종목·일정·1RM·RPE 요구를 확인한다. 연구 참여 조건과 추천 자격을 구분한다.
- 산출물: 버전이 고정된 실행 구성, 대상/필요 입력, 선택 가능한 루틴 목록, 시작 API.
- 인수: 각 지원 시나리오에서 실제 DB 조회 → 입력 충족 → 첫 세션 생성. 대상 밖·입력 부족·미공개를 서로 다른 응답으로 표시한다.
- 차단: 현재 DB research_preview 6개(선택안9개), suspended 1개. 공개 적용 검토와 배포 인증/수행 저장 검증이 완료되지 않았다.
- 제외: 임의 숙련도 라벨만 붙여 공개하거나 미승인 플래그를 제거하는 방식.

## 2. 실제 인증과 1RM·루틴 선택 저장
- Supabase 로그인 토큰을 서버에서 검증한 소유자를 기준으로 모든 저장/조회 권한을 제한한다.
- 1RM 측정/추정·단위·시간 보존; 프로그램 시작 기준은 고정한다.
- 선택한 programme/source/rule 버전과 동의 범위를 저장한다.
- 운영 저장소는 Supabase Postgres로 연결하는 방향으로 준비한다. 현재 SQLite 원장과 기존 iOS workout_snapshots는 자동 병합하지 않는다.
- 인수: 실제 두 사용자로 생성/재조회/타인 접근 차단; 토큰 만료·인증 서버 장애 구분.
- 의존성: 운영 서버의 DB 연결 정보, 해당 환경에서 실제 사용할 테스트 로그인 세션. 비밀값은 저장소에 기록하지 않는다.

## 3. 수행·변경·휴식·중단·완료의 영속 저장
- 기존 검증된 Python 계산을 유지하고 저장소 계층을 운영 DB에 연결한다.
- 요청 ID와 revision으로 중복/동시 변경을 처리하고 원 목표·선택·실제·변경 사유를 보존한다.
- 프로그램/운동/세트/이벤트가 같은 소유자·버전으로 연결되어야 한다.
- 명시적 interrupt와 서버 무활동 중단도 프로그램 종료 평가까지 동작해야 한다.
- 인수: 감량/휴식 변경/중단/완료를 실제 DB에 저장; 서버 프로세스 교체 후 동일 값 반환.
- 데이터 이전은 별도 검토: 기존 iOS 기록을 삭제하거나 새 원장 완료값으로 추정 변환하지 않는다.

## 4. 재접속과 다음 운동
- 클라이언트가 instance ID를 잃어도 본인 프로그램 목록을 조회하고 기존 GET 상세/next-session으로 복구한다.
- 미전송 이벤트를 동기화한 후 무활동 중단을 확인한다. 동시 수정·오래된 참조는 충돌로 반환한다.
- 중단 상태는 재개로 바꾸지 않는다. 남은 세트를 다음 운동에 자동 누적하지 않는다.
- 인수: 새 클라이언트에서 목록 → 원장 → 종료 결과 → 다음 회차; 다른 사용자와 목록 격리.
- 종료 결과가 없는 경우와 미기록 세트를 실패/0으로 보간하지 않는다.

## 5. 배포 HTTPS 인수
- Vercel의 실제 프로젝트·런타임·서버 환경변수를 확인하고 기존 프로젝트의 preview 배포에서 검증한다.
- DB 연결은 서버리스에 맞는 영속 Postgres 경로를 사용한다. 로컬 파일을 운영 영속 저장으로 간주하지 않는다.
- 체크: health, 실제 인증, 카탈로그 조회, 1RM 등록, 프로그램 생성, 운동 시작/이벤트/결과, 프로세스 경계를 넘는 재조회, 다음 회차.
- 인증/카탈로그 대역을 쓰지 않은 실행 결과와 환경·commit·요청 ID를 비밀값 없이 기록한다.
- 배포 접근 실패 시 원인과 필요한 연결만 보고한다. 로컬 테스트 결과를 운영 성공으로 표시하지 않는다.

## 실행 순서와 병렬 가능 범위
1번 공급 검토와 2번 저장소 연결은 함께 준비한다. 3번은 2번의 운영 저장 계약에 의존한다.
4번의 재접속 API와 종료 경계 수정은 지금 구현 가능하다. 5번은 실제 인증·DB·Vercel 연결 후 수행한다.
iOS 연결은 위 인수 흐름이 통과한 API 계약을 기준으로 진행한다. AI·과금·커뮤니티는 이 인수에 포함하지 않는다.

## 마지막 연결 관측 — 2026-10-17, 재개 시 재확인
- Supabase 관리 연결 성공. 실제 카탈로그 상태 재조회 완료.
- Vercel CLI 57.0.0 설치, 인증 조회는 fetch failed로 실패. HTTP 직접 조회는 200이지만 Content-Type=text/html이며 JSON으로 읽히지 않았다. 인증 성공/프로젝트/환경변수는 미확인이다. 오류 3회 이후 같은 요청 반복을 중단했다.
- 현재 프로세스에는 DATABASE_URL/SUPABASE_DB_URL이 설정되지 않았다. 기존 배포 환경의 설정 유무는 미확인이다.
- 실패 원인을 확인하기 전 새 호스팅/DB 비밀번호 변경/인증 우회는 진행하지 않는다.

## Postgres 원장 구현 체크포인트
- 서버 전용 WORKOUT_POSTGRES_DSN: 기존 Supabase 프로젝트의 transaction-pooler 연결 문자열을 배포 환경의 secret으로 설정한다. 브라우저/iOS/응답/로그/저장소에 노출하지 않는다.
- WORKOUT_DB_SSLROOTCERT: 기본 system(libpq17 이상), 필요한 경우 서버에 배치한 신뢰할 CA 파일 경로. 인증서 검증을 끄지 않는다.
- 서버가 먼저 Supabase Auth로 사용자 UUID를 검증한다. DB 연결은 authenticated 역할로 낮추고 해당 소유자만 RLS로 허용한다. 이 역할 전환 권한을 실제 배포 연결에서 확인해야 한다.
- execution_private는 Data API 노출 스키마에 추가하지 않는다. 마이그레이션은 관리 경로에서만 실행하며 HTTP 요청 중 DDL은 실행하지 않는다.
- 현재 실제 DB 테이블/RLS 검증은 완료. Python driver와 DB를 연결한 종단 수행/동시 요청/재시작 검증은 미완료다. 새 7개 테스트는 transport 계약 검증이며 이를 대체하지 않는다.
- 공개 카탈로그 승인, 사용자 적합성 판단, 기존 기록 이전은 이 마이그레이션의 범위가 아니다.
- 성능 advisor는 기존 public 인덱스 미사용 INFO3건만 반환했다. 새 원장 경고는 없으며, 관측 사용량 부족을 이유로 기존 인덱스를 삭제하지 않았다. 진단: https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index

## 사용자 재확정과 다섯 질문 — 2026-10-17
로그인을 유지한다. 무로그인 체험은 작업 대상에서 제외한다. 루틴 데이터 준비가 우선이며 Vercel 접근 복구와 독립적으로 진행한다.
1. 구간별 선택/시작 데이터(2026-10-18 갱신): DB6개 정의/9개 선택안의 전체 회차·부하 방식·입력을 API routine_options에 연결. 입문 시작 경로와 공개 적용 범위는 미완료.
2. 근거/변경 구분: 원 정의/버전을 유지하고 각 선택지의 조정/한계/원문 정의 참조를 제공. 추가 초급후보3편은 누락을 명시해 실행 목록에서 제외.
3. 로그인 후 중량 입력/선택/시작: 내부 코드 존재. 실제 인증과 서버 환경 인수는 미완료.
4. 수행 변경/휴식/미완료/중단 결과: 기존 API와 회귀 검사 유지. 운영 DB 종단 검증 미완료.
5. 재접속/다음 회차: 목록/기록/다음 세션 코드 존재. 실제 배포/앱 검증 미완료.
다음은 준비된 네 종목 데이터로 실제 로그인한 배포 서버/영속 저장 흐름을 검증하고 지원 범위의 공개 적용 결정을 마치는 것이다. 새 후보 수집으로 우회하거나 9개 선택안을 독립된 연구9개로 보고하지 않는다.
