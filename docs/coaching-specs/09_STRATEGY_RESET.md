# 진행 전략 재검토 및 실행 계획 — 2026-10-13

상태: 저장소 d2dea2e 기준 코드·명세 대조와 반례 실행. 독립 전문가 검토나 사용자 실험이 아니다.
이 문서의 우선순위가 07/08 문서의 다음 작업 순서를 대체한다. 과거 구현 기록은 삭제하지 않는다.

## 판정

일부 매몰됐다. 재사용 가능한 기록·출처·버전 기반은 만들었지만,
연구 추출 및 설명 API의 증가를 실제 코칭 경험의 전진처럼 다루기 시작했다.
서비스 원칙은 유지한다. 구현 순서와 완료 기준을 바꾼다.
논문을 더 모으는 일과 앱 연결 중 하나만 택하지 않는다.
지원하려는 한 사용자 흐름에 필요한 근거와 실행 경험을 함께 완성한다.

## 매몰 원인과 중단할 작업

- 측정하기 쉬운 논문 수·API 수·테스트 수가 핵심 흐름 완성도를 대신했다.
- 접근 가능한 연구 한 편을 충실히 재현하는 일이 지원 사용자와 SBD 전체 설계를 대신했다.
- 근거 공백을 정직하게 밝히는 것과 사용자가 다음에 무엇을 할지 도와주는 것을 함께 만들지 못했다.
- 별도 context API를 더 늘리면 기존 guides와 설명·안전 판단이 계속 중복될 수 있다.
- 문서마다 미결정을 추가하면서 담당 산출물·종료 조건 없는 검토 대기가 누적됐다.

보류: 새 설명 전용 API, 고정 개수 논문 수집, 추가 로고/레벨 디자인,
유사 사용자 추천·커뮤니티, 범용 규칙 DSL, 실사용 검증 전 모든 수준 지원,
새 연구를 바로 공개하는 자동화. 기존 자산 삭제는 하지 않는다.

## 개선된 진행 순서와 완료 기준

### S0 — 신뢰 가능한 실행 바닥
선행 없음. 다음 구현의 첫 작업.
- 통증·휴식·결측 반례 수정 및 버전 영향 기록.
- 공개 가능 상태와 내부 연구 시연 상태 분리.
- CI 의존성과 원문 검증 누락 해결, 기존 자동 배치의 실제 쓰기 범위 확인.
완료: 동일 사건에 API별 상반된 안내 없음; 미검토 공개 우회 차단;
깨끗한 실행 환경에서 필수 테스트의 실행/미실행을 구분한 결과.
이 단계의 완료는 과학적 검토 완료가 아니다.

### S1 — 지원 대상과 하나의 완결된 코칭 흐름
S0의 구현과 함께 설계 가능, 실제 공개는 S0 이후.
초기 가설: 바벨 SBD 경험이 있으며 중량 향상을 원하고 기본 동작을 독립 수행하는 성인,
한 종류의 훈련 환경과 주당 일정부터 지원.
이 가설의 대상·일정·제외 기준은 근거 검토로 확정한다. 성별/나이를 특정 연구 편의대로 확정하지 않는다.
- 의사결정 지도: 시작 부하 / 다음 세트 / 다음 세션 / 휴식 / 일정 변경 / 평가.
- 각 결정에 직접 근거, 종합 판단, 제품 규칙, 사용자 선택, 아직 지원 안 함을 명시.
- 완주 예시와 감량·일정 지연 예시를 같은 흐름으로 설계.
완료: 사용자가 시작부터 다음 운동까지 해야 할 행동, 필요한 입력, 예외와 출처가 명확함.
해당 범위를 뒷받침하지 못하면 범위를 좁히거나 연구 재현 시연으로 명시한다.

### S2 — 결정 중심 근거 묶음
S1 결정마다 기존 후보를 선별하고 빠진 핵심·상반 연구를 추가 탐색.
먼저 SBD 직접 대상 및 관련 결과를 확인하고, 간접 근거는 적용 근거와 한계를 별도 기록.
논문마다 별도 루틴을 만드는 대신 보고서-연구-실험군-결과-규칙 연결을 정리한다.
출판 시점·검색 순위·논문 수를 품질 점수로 쓰지 않는다.
전문 접근 불가, 정정/철회 미확인, 조건 미보고를 숨기지 않는다.
완료: 초기 모든 결정에 검토된 규칙 또는 구체적인 사용자 선택 경로가 있음.
추가 검색이 어떤 결정을 바꿀 수 있는지 설명되지 않으면 그 수집은 우선순위를 낮춘다.
검토자 역량·범위·책임을 실제로 확보하기 전 독립 승인을 선언하지 않는다.

### S3 — 기존 기록을 다음 행동에 연결하는 최소 구현
S1/S2에서 정의한 한 흐름만 구현.
- 같은 프로그램·동작의 이전 목표/실제/변경 사유 표시.
- 비교 조건이 다른 기록의 차이 표시 및 자동 환산 제한.
- 사용자가 과거 중량을 선택하면 출처=user_choice로 기록.
- 검토된 조정 제안은 생성→확인→적용→수행을 연결하고 수정/취소·stale 처리.
- 종료 평가와 미측정 상태, 다음 계획 선택 연결.
완료: 기록이 다음 선택에 영향을 준 이유를 재현 가능한 예제로 확인.
단순 평균·최고 중량·논문 평균 성장률로 처방하지 않는다.

### S4 — iPhone에서 흐름 검증
S3가 전부 끝날 때까지 화면 작업을 기다리지 않는다.
S0 이후 L0/L1 흐름부터 한 사용 경로를 앱에 연결하고 단계적으로 확장.
기존 디자인 토큰 유지; 논문 상세는 펼쳐보기, 다음 행동이 첫 화면.
실제 저장/재실행/오프라인 복구 경계와 삭제·정정 기능 포함.
완료: 1RM 입력→운동→감량→휴식 단축→중단/완료→재실행→다음 세션을 실기기에서 수행,
근거 설명과 목표/실제 차이를 사용자 스스로 구분할 수 있음.

### S5 — 사용성 검증과 확대 결정
현재 경쟁 우위와 효과 우월성은 가설이다.
관찰 항목: 도움 없이 다음 행동 선택, 입력 누락·오류, 근거 설명 이해,
기록/복구 성공, 이전 기록 참고의 실제 유용성, 중도 이탈 이유.
통과 조건은 관찰 전에 기록하고 사후 결과에 맞춰 바꾸지 않는다.
사용성 검증과 근력 효과 검증은 별도다. 기록 앱 대비 선택 유용성이 확인되지 않으면
근거 카드 확대를 멈추고 결정 흐름을 수정한다.
다양한 사용자·일정·보조 운동·회복·정체·새 연구 감시는 검증된 흐름부터 확대한다.

## 다섯 가지 다음 검토 질문
질문에 지금 답할 때까지 작업을 멈추라는 뜻이 아니다.
1. 처음 지원할 사용자가 현재 가장 자주 막히는 결정은 무엇인가?
2. 그 결정을 위해 반드시 필요한 근거와 없어도 되는 정보는 무엇인가?
3. 연구 표본과 다른 사용자를 어떤 근거로 포함하거나 제외하는가?
4. 이전 기록이 다음 선택을 바꾼 것을 어떤 실제 예제로 확인할 것인가?
5. 단순 기록 앱보다 유용하지 않다고 판정할 관찰 결과는 무엇인가?

## 이번 검토에서 하지 않은 일
문서·계획 수정과 반례 확인만 수행했다. 위 결함의 제품 코드 수정,
운영 배치 중단, DB 승인 상태 변경, 앱 배포는 하지 않았다.
S0부터 수정한 뒤 각 항목에 구현 커밋과 검증 결과를 붙인다.

새 프레임워크·데이터 플랫폼·범용 설문 엔진·AI 분류기를 추가하지 않는다.

### 다음 실제 작업
S0 검증을 마무리한 뒤 '중량 변경→사유 기록→운동 종료→다음 운동 참고' 한 흐름의
입력 및 응답 계약을 먼저 구현한다. 질문과 저장 필드에는 실제 사용처가 있어야 한다.
임상 통증 관리로 범위를 확대하지 않는다. 통증 자기보고의 기록과 코칭 분기만 다룬다.

### UX 제안: 변경은 먼저 저장하고 사유는 짧게 묻기
- 중량 변경은 즉시 저장. '바꾼 이유가 있나요?' 칩을 해당 세트 근처에 표시.
- 기본 칩: 힘이 부족했어요 / 통증·불편함 / 자세가 흐트러졌어요 /
  장비 때문에 / 계획을 바꿨어요 / 기타. 별도 '건너뛰기'.
- 시간 부족은 세트 생략·운동 종료 문맥에서 우선 노출. 모든 행동에 같은 칩을 나열하지 않는다.
- 증량 문맥은 '여유가 있었어요 / 계획대로 / 장비 때문에 / 기타'로 바꾼다.
- 기본 선택 없음. 다중 사유를 지원하되 필수 개수를 요구하지 않는다.
- 사유를 답하지 않아도 기록과 종료가 가능해야 한다. 입력 없음과 '모름'은 별도 값이다.
- 통증 선택 시 현재 세트 진행을 자동 확정하지 않고 일시정지·종료 선택을 제공한다.
  자세한 부위·점수·기간 질문은 그것을 사용할 검토된 분기가 생기기 전에는 수집하지 않는다.
- 휴식 후 세트 화면에 동일 사유를 반복 요구하지 않는다.
- 사유는 나중에 추가·수정 가능. 과거 선택을 기본값으로 자동 채우지 않는다.
- '기타'의 자유 입력은 선택 사항이며 개인 정보가 포함될 수 있으므로 공유 기본값에서 제외.
이 문구·칩 개수는 제품 가설이다. 사용자 관찰로 변경하며 과학적 척도로 광고하지 않는다.

### 최소 데이터 계약
기존 이벤트 저장 구조를 확장한다. 새 데이터베이스를 만들지 않는다.
- 수행 사실: event_id, workout_id, set_id, 동작, 발생 시각/서버 수신 시각,
  원 목표·변경 전/후 중량(kg), 실제 반복, 목표/실제 휴식, programme/rule/1RM 참조.
- 사유: reason_codes[], reason_schema_version, response_status,
  reported_by=user, recorded_at, optional_note.
- response_status: answered / unknown / declined / not_asked.
  asked 여부를 모르는 기존 null은 별도의 legacy_unspecified로 유지한다.
- 선택지 문자열과 영구 코드를 분리한다. 화면 카피 변경이 과거 코드를 바꾸지 않는다.
- 자기보고 effort_insufficient와 관측된 목표 반복 미달은 서로 다른 필드다.
  fatigue라는 기존 코드에서 새 effort_insufficient를 사실처럼 역추정하지 않는다.
- 사유 정정: 새 이벤트가 supersedes_event_id로 기존 사유를 참조.
  원본 로그를 덮어쓰지 않되 삭제 요구·보유 정책은 별도로 적용한다.
- 앱 해석: decision_id, input_event_ids/revision, rule_version, 근거 참조,
  후보·선택·적용 여부·결과를 사유와 분리해 저장.
- 지금 세트/이후 세트/운동 전체 변경 범위를 명시한다.
  첫 구현은 현재 세트만. 사용자가 '남은 세트에도 적용'을 선택할 때만 확장한다.

### 사유별로 무엇이 달라지는가
| 입력/기록 | 지금 | 다음 운동 | 금지 |
| --- | --- | --- | --- |
| 힘 부족 + 반복 미달 | 실제값 보존, 적용 가능한 규칙 확인 | 같은 조건의 목표/수행/사유를 함께 제시 | 힘 부족 칩만으로 1RM 하향 |
| 통증·불편함 | 일시정지와 기록·종료 경로, 자동 부하 제안 억제 | 이전 통증 기록을 표시하고 현재 상태 확인 경로 필요 | 진단, 감량하면 안전하다는 설명 |
| 자세 흐트러짐 | 기술적 중단을 구분 | 동작/조건 차이와 함께 참고 | 근육의 반복 실패와 동일 공식 적용 |
| 장비 | 실제 장비/중량 변경 보존 | 같은 장비가 아닐 때 비교 제한 | 장비 차이를 근력 저하로 간주 |
| 시간 | 생략·중단과 수행 미달 분리 | 일정 선택에 참고, 남은 분량 자동 이월 안 함 | 못 했다는 이유로 증량/감량 |
| 계획 변경/기타/미응답 | 사실 기록 유지 | 비교 한계 표시, 직접 선택 지원 | 빈값을 정상·피로로 채움 |
| 여러 사유 중 통증 포함 | 통증 분기 우선 | 복합 사유 그대로 보존 | 다수결·평균 점수로 통증 제외 |

근거가 제안 값을 지원하지 못해도 '지난번 목표 80 kg, 실제 75 kg, 힘 부족이라고 기록'
같은 참고와 사용자 직접 중량 선택은 제공한다. 그 75 kg을 최적 처방으로 바꾸지 않는다.

### 데이터셋의 적대적 검토
- 칩 데이터는 자기보고다. 실제 원인/진단/정답 라벨이 아니다.
- 질문을 받은 경우에만 응답하므로 전체 운동의 통증/피로 발생률로 일반화하지 않는다.
- 모든 변경 이벤트를 분모로 두고 asked/answered/unknown/declined를 나눠 본다.
- 질문이 과도해 무작위 선택이 늘면 칩을 줄이거나 빈도를 낮춘다.
- 사후 사유가 변경 이전의 결정을 정당화한 것처럼 시간 순서를 뒤집지 않는다.
- 낮춘 중량으로 완수했다는 기록은 그 감량이 성장을 유발했다는 인과 증거가 아니다.
- 보유 목적은 먼저 개인 기록·설명·검토된 규칙 적용이다.
  향후 모델 학습·다른 사용자 추천·커뮤니티 공유는 각각 별도 범위와 동의·삭제 설계가 필요하다.
- 자유 입력을 자동으로 진단/감정 라벨로 바꾸지 않는다.
- 수집했지만 어떤 화면/결정에도 쓰이지 않는 필드는 추가하지 않는다.

### 이후 작업 묶음과 인수 조건
| 순서 | 산출물 | 통과 조건 |
| --- | --- | --- |
| A | S0 오류 수정·공개 경계·재현 테스트 | 통증/종료 휴식/미기록 반례 및 과거 버전 경계 확인 |
| B | 변경 사유 계약·작은 화면 흐름 | 감량/증량/생략/종료별 적절한 칩, 건너뛰어도 실제 수행 저장 |
| C | 기존 이벤트에 사유 추가·정정 | 중복 요청·오프라인 재전송·사후 정정·복합 사유가 데이터 손실 없이 연결 |
| D | 다음 세션 참고/선택 | 동일 조건과 차이를 표시, user_choice와 연구 제안을 구분 |
| E | 해당 결정의 근거 보완 | 원문·상반 결과·적용 한계로 결정 규칙을 검토. 논문 수 목표 없음 |
| F | 앱 실기기·한 프로그램 평가 | 시작→변경→기록→다음 선택→기간 종료를 사용자가 수행 |
D/E는 함께 진행한다. 근거 카드만 먼저 늘리지 않는다.
선택지 사용률·미응답률·수정률·입력 시간은 UX 관찰값이며 효과 검증값이 아니다.

다음 다섯 검토 질문:
1. 사유 입력이 없을 때도 기록·종료·다음 선택을 할 수 있는가?
2. 통증과 힘 부족을 함께 선택하면 모든 화면이 같은 처리를 하는가?
3. 오늘 사유를 내일 정정하면 미적용 제안만 다시 계산하는가?
4. 어떤 입력이 실제로 다음 선택을 바꾸며, 쓰지 않는 입력은 무엇인가?
5. 이 흐름이 기록만 하는 앱보다 유용하다는 것을 사용자가 보여주는가?

### S0 구현 체크포인트
- 실행 계산 v2: 통증 중량 변경도 pause, 통증 이력 이후 부하 제안 억제,
  종료/종목 전환 휴식을 세트 사이 휴식 부족 합계에서 제외, 미기록은 확정 % 대신 범위.
- 기존 v1 기록: 원 계산 모듈 보존, 기록 열람·종료·기존 요청 재시도 허용.
  새 수행 이벤트는 거부. 기존 진행 중 운동의 자동 마이그레이션은 미구현이다.
  이 제한은 배포 전 사용자 영향 확인이 필요한 호환성 변경이다.
- v3 미승인 프로그램 생성·새 세션 시작: 서버 관리 COACHING_PREVIEW_OWNER_IDS의
  내부 계정만 허용. 과학적 승인 기능이 아니라 내부 시연 경계다.
  기존 운동 읽기·기록·종료와 동일 세션 시작 재시도는 유지.
- 기존 배치 import 코드를 확인하니 공개 가능한 자료 적재를 거부한다.
  자동 공개가 실제 발생했다는 주장은 하지 않는다. Actions 운영 로그는 미확인이다.
- 테스트 의존성 고정, 주간 CI에 원문 확보 단계 및 skipped를 실패 처리하는 검사 추가.
- 로컬 실제 원문 캐시 환경에서 145개 테스트, 건너뜀 없이 통과.
  GitHub 실행 및 배포 환경 검증은 아직 수행하지 않았다.
- 프리셋 칩·다중 사유·정정 이벤트는 위 설계 상태이며 이번 코드 변경에 포함되지 않았다.
