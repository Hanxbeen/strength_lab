# 연구 업데이트·출시 검증 명세

문서 ID: OPS · 버전 0.2 · 2026-10-12 KST
상태: 운영 설계안. 스케줄·알림·배포의 실제 가동을 선언하지 않는다.  
연결 원칙: P01~P10 · 선행: [개인화](03_PERSONALIZATION.md)

## 1. 운영 경계

초기 작업은 질문별 근거 체계 구축이다. 운영 배치는 새로운 자료·정정·철회를 찾아 기존 판단에 영향을 주는지 검토할 후보를 만든다. 배치 계정에는 운영 처방 배포 권한을 주지 않는다.

운영 상태는 scheduled / running / succeeded / partial / failed / paused로 관리하며 last_attempt, last_success, covered_until, source별 완료 상태를 공개 운영 대시보드에 둔다. 워크플로 파일 작성·예약 등록·첫 성공 실행·지속 운영을 구분한다.

## 2. 주간 감시

OPS-01. 기본 목표 주기는 주 1회이며 요일·시각·시간대는 deployment_config에 지정한다. 날짜순 신규 검색과 기존 채택 근거의 정정·철회 재확인을 함께 수행한다. 발행일만으로 검색하지 않고 색인/수정 시각과 중복 제거를 사용해 늦은 색인을 다룬다.

BatchRun에는 run_id, query_versions, 시작/종료, source별 커서와 완료 범위, 발견·중복·변경·실패 건수, 모델/프롬프트/추출 버전, 다음 시도 상태를 남긴다. 일부 검색원 실패 시 마지막 성공 범위를 덮지 않는다. 실패한 감시를 ‘새 연구 없음’으로 표시하지 않는다.

원문 해시 변경은 변경 감지 신호일 뿐 과학적 결론 변경의 확정이 아니다. 서식·메타데이터·내용 변경을 비교하고, 출판사의 정정/철회 공지와 연결한다. 추출 실패 시 구 버전 결과와 실패 상태를 유지하며 빈 카탈로그로 대체하지 않는다.

조회량 제한·재시도·백오프·수동 재개를 지원한다. 구체 호출 수·시간 제한은 제공자의 정책과 실제 부하에 맞춰 배포 전에 정한다. 접근 제한을 우회하지 않는다. 일시 장애는 재시도 가능한 상태로 남긴다.

## 3. 영향 분석과 알림

OPS-02. 후보 알림은 원문 식별자, 변경 종류, 연결된 Q/claim/rule/programme, 새 결과와 기존 판단의 관계, 직접성·불확실성, 영향받을 기능·사용자 인스턴스 수, 확인이 필요한 사항을 포함한다.

관계는 supports / challenges / narrows_scope / extends_scope / correction / retraction / unresolved로 구분한다. AI가 생성한 관계는 proposed이며 검토 전 사실로 확정하지 않는다. 검색 랭킹이나 AI 확신 점수만으로 사용자 코칭을 바꾸지 않는다.

일반 연구 추가, 추출 오류, 근거 철회는 별도 우선순위로 전달한다. 운영 담당자 수신 채널·중복 억제·확인 상태·에스컬레이션 경로를 설정한다. 알림 SLA와 확인 책임자가 정해지지 않았으면 감시의 운영 준비가 끝난 것으로 보지 않는다. 사용자에게 이메일/메시지 등을 보내는 실제 기능은 별도의 수신 동의와 채널 정책에 따른다.

## 4. 검토·배포·롤백

EVD의 candidate → reviewed → release_eligible은 검토 상태다. 별도 Release는 staged → active → deprecated 또는 suspended 상태다. rule/programme 버전은 내용 변경 시 새로 발행하고 기존 정의를 조용히 수정하지 않는다.

OPS-03. ReleaseManifest는 release_id, 정의·규칙·근거 버전/해시, 클라이언트 최소 계약, migration/rollback 계획, 검토 책임자, 알려진 제한, 활성 기능과 비활성 이유를 가진다. 검토자·승인 시각을 시스템이 임의 생성하지 않는다.

| 역할 | 책임 | 미확보 시 |
|---|---|---|
| 문헌 검토 담당 | 검색·추출·제외·공백 기록 | 해당 질문 검토 미완료 |
| 도메인 검토 담당 | 연구 해석·적용 범위·처방 구성 검토 | 해당 자동 처방 비활성 |
| 제품/데이터 담당 | 입력 부담·설명·계산·개인정보 처리 | 관련 기능 출시 보류 |
| 구현/배포 담당 | 계약·접근 통제·복구·감시·배포 확인 | 운영 배포 미완료 |

한 사람이 여러 역할을 맡을 수 있지만 자동 처방의 핵심 해석은 EVD-10의 별도 확인 기준을 충족해야 한다. 과학적 검토와 코드 검토의 완료 상태를 각각 기록한다. 사람 이름을 아직 지정하지 않은 것은 이 문서 작성 실패가 아니라 기능 활성화 전 해결할 운영 공백이다.

일반 업데이트: 신규 인스턴스에 적용하고 기존 인스턴스는 고정 버전을 유지한다. 기존 사용자가 전환을 선택하면 이전·새 계획과 이유를 보존한다. 효과 비교에서는 전환 시점을 표시한다.

OPS-04. 철회·심각한 추출 오류 등 영향이 의심되면 해당 근거에 의존하는 신규 자동 처방을 우선 보류할 수 있다. 사실 확인 및 의존성 평가 후 suspended 범위를 정한다. 진행 중 사용자에게 영향을 설명하고 선택/재검토 경로를 제공하되 자동 대체 처방을 생성하지 않는다. 기록 읽기·정정·종료·내보내기는 유지한다. 과거 기록 보존과 현재 추천 중단은 별개다.

롤백은 카탈로그/규칙 활성 포인터를 이전 검증 버전으로 되돌리는 작업이다. 새 버전으로 이미 수행한 운동을 없애지 않는다. 이전 버전도 문제 근거에 의존하면 그 버전으로 되돌리지 않고 해당 기능을 중단한다.

suspended는 active뿐 아니라 staged/deprecated 상태에도 적용할 수 있다. 철회 신호만으로 모든 관련 연구가 무효라고 단정하지 않고 연결 근거별 영향 판단을 기록한다. 오프라인 사용자가 최신 중단 상태를 즉시 받을 수 없다는 한계를 전제로 캐시 유효기간·재접속 확인·기록 유지 정책을 배포 조건에 포함한다.

## 5. 출시 전 검증 층위

| 층위 | 확인 대상 | 통과가 뜻하지 않는 것 |
|---|---|---|
| A 출처·추출 | 원문 위치·단위·비교군·코호트·누락, 독립 대조 | 추천 효과 입증 |
| B 과학적 해석 | 직접성·상충·적용·대체 규칙·전체 프로그램 | 모든 사용자에게 효과 보장 |
| C 계산·계약 | 목표/실제 분리·분모·정정·상태·결측·버전 | 유입·유지·성장 우위 |
| D 운영·보안 | 인증·소유권·부하·복구·백업·마이그레이션·알림 | 실제 장기 운영 완료 |
| E 사용성·가치 | 이해도·입력 부담·다음 선택의 유용성·지속 | 인과적 운동 효과 |
| F 효과 평가 | 미리 정한 비교 설계·결과·결측·분석 | 다른 대상·조건으로의 무제한 일반화 |

OPS-05. 기능별로 필요한 검증 층위를 지정한다. 기록 기능은 과학적 자동 처방과 같은 검증 범위를 요구하지 않지만, 효과·우월성을 주장하려면 그 주장에 맞는 검증을 갖춰야 한다. 기능이 제한돼 있다는 이유로 기록·열람까지 모두 차단하지 않는다.

## 6. 필수 반례 시나리오

아래는 구현 후 실행할 인수 시나리오다. 이 문서 작성 중 실제 테스트가 모두 수행됐다는 뜻이 아니다.

1. 같은 참여자의 여러 보고서와 메타분석을 중복 집계하지 않는다.
2. 비교군에도 수행한 공통 훈련이 프로그램에서 빠지면 배포를 차단한다.
3. 보고하지 않은 휴식·진행 수치를 AI가 채웠을 때 candidate로 격리한다.
4. 단일 연구와 종합 판단이 충돌하면 자동 처방을 중지하고 원인과 fallback을 낸다.
5. 1RM 미등록 상태로 마지막 주차 선택을 통해 시작 조건을 우회하지 못한다.
6. 목표 80 kg을 72 kg으로 바꿔도 최초 목표와 실제값을 함께 복구한다.
7. 0 부가 중량과 바벨 전체 중량 0을 같은 의미로 처리하지 않는다.
8. 일시정지 중 휴식 종료 버튼 등 불가능한 행동을 응답하지 않는다.
9. 앱 종료·오프라인·시계 변경 후 휴식을 확정할 수 없으면 미확인으로 남긴다.
10. 기록 정정은 파생 지표와 미적용 제안에 반영되고 이미 수행한 처방은 유지된다.
11. 새 카탈로그 배포 직후 동일 시작 요청을 재시도해도 최초 결과가 반환된다.
12. 요청/이력 한도에 도달해도 기록 열람·종료·복구가 가능하다.
13. 근거 철회 시 신규 추천만 멈추고 기존 사용자 기록을 삭제하지 않는다.
14. 계정 전환·삭제·다른 기기 재접속에서 소유권이 섞이지 않는다.
15. 미기록·중도 이탈을 성공/실패로 임의 치환하거나 완료자만 공개 집계하지 않는다.
16. 입력값이나 원문에 포함된 명령 문구가 배포 승인·권한 변경으로 실행되지 않는다.

## 7. 제품 가치와 효과 평가

출시 검증 계획에는 지표 정의·분모·수집 기간·목표/중단 기준을 실험 시작 전에 기록한다. 지표값은 실제 기준선 조사 전 임의로 채우지 않는다.

- 사용성: 도움 없이 시작·수정·중단·복구 가능한가, 출처/목표/실제를 구별하는가, 질문 부담은 어떤가.
- 운영: 유실·중복·복구 실패·규칙 충돌·추출 미확인·감시 실패를 추적한다.
- 가치: 다음 훈련 선택의 도움, 지속률, 추천 수락뿐 아니라 거절 이유와 사용자 변경을 관찰한다.
- 수행: 비교 가능한 평가 조건의 변화, 수행률·종료 평가 누락·이탈을 함께 보고한다.

무작위 또는 적절한 비교 설계 없이 사용자 전후 기록만으로 앱의 인과적 효과를 주장하지 않는다. 훈련·측정에 익숙해지는 효과, 체중·다른 운동 등 혼입 요인을 기록한다. 알고리즘 변경 전후 비교도 선택 편향과 기간 차이를 고려한다. 효과를 입증했다고 표기할 분석 계획은 별도 검토한다.

## 8. 개인정보·공유·보존

OPS-06. 개인 기록, 원문 근거, 공개 사례를 다른 접근 범위로 관리한다. 인증/권한은 서버가 검증하며 비밀키를 클라이언트에 넣지 않는다. 로그·오류·AI 입력에 불필요한 개인 정보나 토큰을 넣지 않는다.

서비스 제공에 필요한 기록 처리, 선택적 연구/추천 분석, 커뮤니티 공유의 사용 목적을 구분한다. 공개 전 미리보기·공개 항목 선택·공유 철회를 제공한다. 익명화 여부를 검증하지 않은 자료를 익명이라고 부르지 않는다.

원칙의 불변 기록은 일상적인 수정 시 과거를 덮어쓰지 않는다는 뜻이다. 개인정보 삭제·동의 철회·보유 기간 만료에 따른 삭제를 금지한다는 뜻이 아니다. 원문/정의의 비개인 버전은 유지할 수 있지만 개인 스냅샷·공유물·검색 인덱스·파생 분석·백업의 삭제/복원 처리 범위를 정해야 한다. 삭제 후 복구로 다시 노출되는 것을 방지한다.

보유 기간·백업 제거 주기·소표본 공개 기준·선택적 처리 동의 UI는 출시 기능별 정책으로 구체화한다. 미정인 경우 해당 개인 데이터 수집·공개 범위를 활성화하지 않는다. 이 문서는 법률 적합성을 확인한 문서가 아니다.

## 9. 구현·운영의 남은 결정

운영 저장소, 인증 연계, 클라이언트 오프라인 동기화, 이전 데이터 마이그레이션, 검토자 지정, 배치 스케줄·알림 채널, 데이터 보존 정책을 실제 환경에서 검증해야 한다. SQLite 프로토타입의 테스트 성공을 Supabase 운영 저장·다중 기기 동기화 완료로 보고하지 않는다.

각 미결정은 owner_role, affected_capability, resolution_evidence, blocking_scope를 가진다. 숫자가 미정이어도 fallback이 명확한 명세는 작성 완료로 볼 수 있다. 단, 그 자동 처방이나 공개 기능의 출시 완료로 간주하지 않는다.
